## Introduction
{:#introduction}

For many years now,
[Linked Data on the Web has existed in many shapes and forms](cite:cites spec:sparqlprot,tpf,smartkg,sage,wisekg,brtpf,passage).
This variety allows the [RDF data model](cite:cites spec:rdf) underpinning the semantic web to be used across many environments, covering various use cases.
Besides a heterogeneity in data,
the Linked Data ecosystem also knows many differing processors to query data from one or many sources.
The modular query engine, [Comunica](cite:cites comunica), was introduced to unionize querying over the different shapes and forms of RDF data, while supporting many data processing techniques.    
Even though Comunica's modular architecture has proven fruitful,
enabling _sustainable_ maintenance of a [SPARQL 1.1](cite:cites spec:sparqllang) query engine supporting many RDF dataset types and query [processing techniques](TODO: query processing techniques supported by comunica),
it was limited to processing basic SPARQL 1.1 queries and, though a query conversion step a [subset of GraphQL](TODO: sparql-graphql paper RT).

This limitation was not arbitrary, but technical.
The parsing and generating software on which Comunica relied to transform a SPARQL string to and from SPARQL algebra was a big monolith.
Modifications to the monolith would thus entail that either:

1. Comunica maintains its own fork of the original project,
2. the Comunica developers submit changes to their parsing software package thereby changing its behavior beyond SPARQL 1.1, or
3. the Comunica developers submit changes to their parsing software package and maintain backward compatibility by introducing many conditionals, thereby complicating that package's maintainability.

Additionally, SPARQL itself has been heterogeneous for many years,
with many SPARQL engines implementing different [dialects](cite:cites geosparql,tsparql,csparql,rdfversioningquerylang) of the SPARQL specification, and adding features ontop of it:
[Virtuoso supports full text search](cite:cites virtuoso-full-text-search),
[Jena supports constructing quads](cite:cites jena-construct-quad), and
[oxigraph supports the built-in Adjust](cite:cites sparql-adjust, oxigraph-adjust).
What's more, 
This existing heterogeneity is projected to grow with the introduction of SPARQL 1.2, 
and it's subsequent [maintenance mode](https://github.com/w3c/sparql-dev/issues/32#issuecomment-2621209920) [](cite:cites rdf12-charter, modular-parsing).


To this end, we created a parser, generator and transformer toolkit called [Traqula](TODO: traqula).
In our ESWC 2026 article we describe how Traqula can be used to easily modify an
existing SPARQL 1.1 or 1.2 parsing setup,
while remaining generic enough to allow future support for other query languages such a [GQL](cite:cites iso-gql), [SHACL compact](cite:cites shacl-compact), or [SHACL rules](cite:cites shacl-rules).

In this article we describe how we will showcase the [Traqula framework](TODO: tarqula) and it's benefits.
We created a web client capable of dynamically creating a parser, generator, and transformer using Traqula,
as well as dynamically creating a query engine using Comunica.
Starting from SPARQL 1.1, the user is able to select whether it wants to support a feature or not, and this choice is then reflected in the Traqula and SPARQL configuration.
Using the configured features, the user can then query remote sources using a provided query interface.
