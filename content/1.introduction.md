## Introduction
{:#introduction}

For many years now,
[Linked Data on the Web has existed in many shapes and forms](cite:cites spec:sparqlprot,tpf,smartkg). <!-- sage,wisekg,brtpf,passage -->
This diversity allows the
<!-- [RDF data model](cite:cites spec:rdf) --> RDF data model
underpinning the Semantic Web to be deployed across a wide range of environments and use cases.
Besides heterogeneity in data publication, the Linked Data ecosystem also contains many different processors that query data from one or multiple sources.<span class="comment" data-author="RT">Are you referring to federation engines? If so, there aren't that many of them.</span>

The modular query engine [Comunica](cite:cites comunica) was introduced to unify querying over these different RDF interfaces while supporting multiple data access and processing techniques .
It's modular architecture has proven effective,
enabling _sustainable_ maintenance of a [SPARQL 1.1](cite:cites spec:sparqllang) query engine that supports many dataset types and execution strategies.
However, Comunica has so far been limited to processing basic SPARQL 1.1 queries and –through conversion step– a [subset of GraphQL](cite:cites graphql-ld).

This limitation was not arbitrary, but technical.
<span class="grammar" data-author="RT">The software used to parse and generate SPARQL queries, responsible for transforming query strings to and from SPARQL algebra,</span>
was implemented as a large monolithic component.
Extending this component would require either:
<!-- -->
1. maintaining a long-term fork
2. introducing language extensions that change the behaviour of the upstream parser beyond SPARQL 1.1, or
3. preserving backward compatibility through extensive conditional logic, ultimately harming maintainability.

At the same time, SPARQL itself has evolved heterogeneously.
Different engines implement their own
[dialects](cite:cites geosparql,tsparql) <!-- csparql,rdfversioningquerylang --> and extensions:
[Virtuoso supports full text search](cite:cites virtuoso-full-text-search),
[Jena supports constructing quads](cite:cites jena-construct-quad), and
[oxigraph supports the built-in Adjust](cite:cites sparql-adjust, oxigraph-adjust).
This diversity is expected to increase further with the emergence of [SPARQL 1.2](cite:cites sparql-1-2) and
its planned [maintenance mode](https://github.com/w3c/sparql-dev/issues/32#issuecomment-2621209920) [](cite:cites rdf12-charter). <!-- modular-parsing -->


To address these challenges, we developed [Traqula](cite:cites traqula), a toolkit for parsing, generating, and transforming query languages.
As described in our ESWC 2026 paper<span class="comment" data-author="RT">You can already cite it, with the note "Accepted for publication".</span>, Traqula enables incremental modification of existing SPARQL 1.1 and SPARQL 1.2 parsing setups while remaining generic enough to support future query languages such as [GQL](cite:cites iso-gql), [SHACL compact](cite:cites shacl-compact), or [SHACL rules](cite:cites shacl-rules).

In this demo paper, we present an interactive showcase of the Traqula framework and its benefits.
We developed a web client that dynamically constructs parsers, generators, and transformers using Traqula,
and dynamically constructs a Comunica query engine also based on the user's choice.
Starting from a SPARQL 1.1 baseline, users can enable or disable language features,
after which the system adapts both the parsing configuration and query engine accordingly.
The configured setup can then be used to query remote data sources through an integrated query interface.
